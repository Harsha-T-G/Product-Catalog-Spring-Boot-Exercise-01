# Database-Backed Authentication Contract

**Status:** Implemented on 2026-09-09; final Java 21 gate verified on 2026-09-10
**Module:** `database-authentication`
**Covers:** `REQ-121`–`REQ-129`, `AC-121`–`AC-127`
**Depends on:** Approved `docs/security-spec.md` and implemented PLAN-W7-01

## Objective

Replace the temporary deny-all identity boundary with PostgreSQL-backed HTTP
Basic authentication. Passwords are stored only as BCrypt hashes, usernames
behave case-insensitively, disabled accounts cannot authenticate, and client
responses do not disclose whether an account exists.

## Data contract

### `app_users`

| Column | PostgreSQL type | Rules |
| --- | --- | --- |
| `id` | `UUID` | Primary key; generated by the application |
| `username` | `VARCHAR(100)` | Required; trimmed before persistence |
| `password_hash` | `VARCHAR(60)` | Required BCrypt hash; never returned or logged |
| `enabled` | `BOOLEAN` | Required; defaults to `TRUE` |
| `created_at` | `TIMESTAMPTZ` | Required; assigned by the application |

The database owns the final username uniqueness guarantee through a unique
index on `LOWER(username)`. Authentication lookup uses the same
case-insensitive comparison. The stored spelling is retained as the principal's
display username; case is not an identity distinction.

### `roles`

| Column | PostgreSQL type | Rules |
| --- | --- | --- |
| `id` | `BIGSERIAL` | Primary key |
| `name` | `VARCHAR(20)` | Required and unique |

The migration inserts exactly `VIEWER`, `EDITOR`, and `ADMIN`. The application
maps them to Spring authorities `ROLE_VIEWER`, `ROLE_EDITOR`, and `ROLE_ADMIN`.

### `app_user_roles`

| Column | PostgreSQL type | Rules |
| --- | --- | --- |
| `user_id` | `UUID` | FK to `app_users`; cascade on user deletion |
| `role_id` | `BIGINT` | FK to `roles` |

The composite primary key prevents duplicate role assignments. Roles are loaded
with the authenticating user in the database-backed identity query.

## Requirements

### REQ-121: Flyway-owned identity schema

Flyway shall create `app_users`, `roles`, and `app_user_roles`. Hibernate shall
continue to validate, not create or update, the schema. The forward-only
exercise rollback is restoring the database or applying a later corrective
migration; an applied migration is never edited in place.

### REQ-122: Persistence mapping

JPA entities and Spring Data repositories shall represent users, roles, and
their mapping without exposing persistence entities through REST endpoints.
User identifiers use UUID and role identifiers use database-generated `Long`.

### REQ-123: Case-insensitive usernames

Repository lookup and database uniqueness shall ignore username case. Input is
trimmed before application persistence. A request for `ALICE` may authenticate
the stored username `alice`; a second `Alice` record is rejected by PostgreSQL.

### REQ-124: Database-backed user loading

A Spring `UserDetailsService` shall load the user and roles from PostgreSQL for
each stateless HTTP Basic authentication attempt. Unknown usernames shall raise
Spring Security's normal username-not-found result and shall not receive a
different client-visible response.

### REQ-125: BCrypt verification

A `BCryptPasswordEncoder` bean shall verify submitted passwords against stored
hashes. Only BCrypt values may be persisted by application user-creation or
development-seeding paths. Password hashes cannot be decoded; authentication is
a one-way hash comparison.

### REQ-126: Disabled accounts

The loaded Spring Security principal shall carry the persisted `enabled` flag.
An account with `enabled=false` shall receive HTTP 401 even when its username
and password are otherwise correct.

### REQ-127: Non-revealing failures

Wrong-password, unknown-username, and disabled-user requests shall all return
the same public HTTP status and Basic challenge. This module does not add
identity-specific messages. The common JSON error body is delivered by the
later `request-observability` module.

### REQ-128: Development-only sample users

The `dev` profile may create one user per required role. Seeding shall run only
when all three passwords are supplied through `CATALOG_VIEWER_PASSWORD`,
`CATALOG_EDITOR_PASSWORD`, and `CATALOG_ADMIN_PASSWORD`. Usernames default to
`viewer`, `editor`, and `admin`, may be overridden by corresponding username
environment variables, and are idempotently skipped when already present.
There is no committed password default.

### REQ-129: Credential configuration

Committed configuration shall contain no database or sample-user password.
Local database credentials and sample-user passwords must be supplied by
environment variables. Tests may use clearly test-only credentials held only in
test code and shall prove their persisted form is BCrypt rather than plaintext.

## Security flow

```text
HTTP Basic header
  -> BasicAuthenticationFilter
  -> AuthenticationManager / DaoAuthenticationProvider
  -> database UserDetailsService
  -> AppUserRepository + roles
  -> BCryptPasswordEncoder comparison
  -> authenticated principal in SecurityContext for this request
```

The stateless policy discards the request security context afterward; the next
request authenticates again from current database state.

## Acceptance criteria

### AC-121: Schema and roles

**Given** an empty PostgreSQL database, **when** Flyway runs, **then** all three
identity tables, foreign keys, the lower-username unique index, and the three
canonical roles exist.

### AC-122: Valid authentication

**Given** an enabled database user with a BCrypt password and role, **when** the
user supplies the correct password with any username case, **then** a protected
request passes authentication.

### AC-123: Invalid password

**Given** an existing enabled user, **when** the password is incorrect, **then**
the response is HTTP 401 with `WWW-Authenticate: Basic`.

### AC-124: Unknown and disabled accounts

**Given** an unknown username or a disabled user with the correct password,
**when** a protected request is made, **then** both responses are externally
indistinguishable HTTP 401 authentication failures.

### AC-125: BCrypt persistence

**Given** a test-only plaintext password, **when** it is encoded and persisted,
**then** the stored value starts with a supported BCrypt prefix, differs from
the submitted value, and matches through the configured encoder.

### AC-126: Case-insensitive uniqueness

**Given** a stored username `catalog-user`, **when** another record attempts to
store `CATALOG-USER`, **then** PostgreSQL rejects the duplicate.

### AC-127: Safe development seeding

**Given** the `dev` profile without all required password variables, **when**
the application starts, **then** it creates no sample users. With all password
variables present, it creates one appropriately assigned and BCrypt-encoded user
per role without logging any password or hash.

## Exclusions

- Endpoint role authorization remains in `role-authorization`.
- User-management REST endpoints remain in `admin-user-management`.
- JSON 401/403 envelopes and trace-aware logs remain in
  `request-observability`.
- JWT, sessions, password reset, account lockout, and password rotation are not
  part of this exercise.
