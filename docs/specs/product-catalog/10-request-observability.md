# Request Observability and Security Error Contract

**Status:** Implemented and verified on 2026-09-10
**Module:** `request-observability`
**Covers:** `REQ-150`–`REQ-163`, `AC-150`–`AC-160`
**Depends on:** Implemented PLAN-W7-02 through PLAN-W7-04

## Trace contract

- Request and response header: `X-Trace-Id`.
- MDC key and error JSON field: `traceId`.
- A caller value is valid only when it is exactly one canonical 36-character
  UUID representation: hexadecimal groups `8-4-4-4-12`, case-insensitive, with
  no surrounding whitespace or control characters.
- A valid value is reused exactly. A missing, blank, malformed, or oversized
  value is replaced with a newly generated lowercase UUID.
- The trace filter applies to every request, places the selected value in a
  request attribute and MDC before downstream processing, sets the response
  header before the chain runs, and removes the MDC key in `finally`.

This deliberately narrow caller format prevents log injection and unbounded MDC
values while remaining interoperable with the UUIDs generated by the service.

## Requirements

### REQ-150: Trace selection and propagation

Every response shall contain `X-Trace-Id`. A valid caller UUID shall be reused;
otherwise the application shall generate a UUID. The same value shall be
available to downstream application and security error handling.

### REQ-151: MDC lifecycle

The selected trace ID shall be present under MDC key `traceId` only while the
request is processed. Cleanup shall occur in a `finally` block and be proven
across consecutive requests on a reused test thread.

### REQ-152: Request completion log

Every request shall produce one completion event containing only safe fields:
`event=request_completed`, trace ID, HTTP method, request URI path without query
string, response status, integer duration in milliseconds, and authenticated
username when available. It shall never include headers, query parameters, or
request/response bodies.

### REQ-153: Safe authenticated identity capture

Successful authentication may expose the current principal name to the outer
request logger through a request attribute. Anonymous and failed-authentication
requests use `username=anonymous`; submitted Basic usernames are not parsed or
logged by the trace filter.

### REQ-154: Common error representation

Application 4xx/5xx errors and Spring Security 401/403 errors shall use the
fields `timestamp`, `status`, `error`, `message`, `path`, `traceId`, and
`fieldErrors`. The former `errorReferenceId` response field is replaced by the
request trace ID. No stack trace, SQL text, entity detail, password data, header,
or internal class name may appear in a response.

### REQ-155: Authentication failure response

Missing, malformed, invalid-password, unknown-user, and disabled-user
authentication shall return the same generic 401 JSON semantics with message
`Authentication is required`, the request trace ID, and a normal HTTP Basic
`WWW-Authenticate` challenge.

### REQ-156: Authorization failure response

An authenticated principal without sufficient permission shall receive 403 JSON
with message `Access is denied` and the request trace ID. Matcher and authority
internals shall not be returned.

### REQ-157: Security event logging

Authentication failure and access denial shall each emit a WARN event with
trace ID, safe path, and outcome. Access denial may include the authenticated
username. Authentication failure shall not log the submitted username,
Authorization header, password, or exception text.

### REQ-158: Application event logging

Successful product creation, stock adjustment, user creation, and user
enable/disable shall emit INFO events with trace ID supplied by MDC and only the
minimum useful identifiers/outcome. Complete DTOs and bodies are forbidden.

### REQ-159: Unexpected failure logging

An unexpected server failure shall emit one ERROR event with trace ID, safe
path, and exception type for server diagnosis. Because exception messages and
stack traces may contain request or credential data, neither is logged by the
generic handler. The client receives only the generic 500 envelope.

### REQ-160: Normal 4xx logging

Normal validation, not-found, duplicate, conflict, authentication, and
authorization outcomes shall not log stack traces. Request completion uses WARN
for 4xx, INFO for successful/redirect responses, and ERROR for 5xx.

### REQ-161: Log-field sanitization

Caller-controlled username and path values written as log fields shall have
control characters replaced and be length bounded. Trace IDs require the UUID
format above and need no additional escaping.

### REQ-162: Logging configuration

The console log pattern shall display MDC `traceId` so application logs inside a
request can be correlated even when an individual event does not repeat the
field in its message.

### REQ-163: Debugging evidence

`docs/debugging-notes.md` shall document VIEWER create denial, duplicate-SKU
409, and negative-stock rollback with an observed trace ID, root cause,
debugging method, status rationale, and sensitive-data check. Automated tests
and captured logs may supply repeatable evidence where an interactive debugger
cannot be recorded in the repository.

## Logging levels

| Level | Use |
| --- | --- |
| DEBUG | Local diagnostic detail that is disabled by default and still contains no secrets |
| INFO | Successful request completion and successful domain state changes |
| WARN | Expected client/security failures (4xx), without stack traces |
| ERROR | Unexpected server failures (5xx), correlated by trace ID |

## Acceptance criteria

- **AC-150:** A valid incoming UUID is reused in the response and MDC.
- **AC-151:** Missing and invalid trace values are replaced with valid UUIDs.
- **AC-152:** MDC is empty after each request and does not leak to the next.
- **AC-153:** Each request completion log contains method, path, status,
  duration, trace ID, and safe username.
- **AC-154:** 401 returns the common JSON envelope, trace header/body match, and
  the Basic challenge remains present.
- **AC-155:** 403 returns the common JSON envelope and matching trace values.
- **AC-156:** Application errors contain the same matching trace header/body.
- **AC-157:** Successful product/stock/user events are logged without bodies or
  credentials.
- **AC-158:** Failed-login/access-denied events are logged without submitted
  credentials or normal-4xx stack traces.
- **AC-159:** Unexpected error output contains trace ID but not exception message
  or response internals.
- **AC-160:** All three required debugging scenarios are documented with
  repeatable evidence.
